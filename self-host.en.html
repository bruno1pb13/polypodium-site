Server documentation

Polypodium works 100% offline. The server is optional: with it you sync your collection across devices, keep a backup off your phone, share gardens with other people, get the weather forecast computed in one place and connect AI assistants. This page covers everything from installation to the API.

Install in 5 minutesDocker Compose, ready-made image, nothing to compile. Connect the appWorkspaces, accounts and shared gardens. Connect an AIClaude, Cursor and other MCP clients. API referenceEvery route under /api/v1.

Overview

The server is a single Dart binary that speaks HTTP/JSON and stores everything in PostgreSQL. Photos live in a folder on disk. It ships as a Docker image at ghcr.io/bruno1pb13/polypodium_server, and the source is open, under the MIT license, at github.com/bruno1pb13/Polypodium_server.

Concepts

  • Account. An email and password on the server. The first account becomes the admin and creates the others; there is no public sign-up after it.
  • Garden. The set of data that gets synced: plants, species, locations, pots, soils, diary entries, photos, pesticides and reminders. Every account has a personal garden and can create more to share with other accounts.
  • Workspace. The app side. Each workspace is a separate database on the device. The local workspace never leaves the device; each remote workspace syncs one garden on one server. Switching workspaces never mixes data.
  • Device. Each app install has a deviceId. The server is just one more peer in the sync: entity IDs are generated on the device and the server never reassigns them.

What runs on the server

ComponentRole
REST API /api/v1Login, sync (pull/push), photos, gardens, administration, weather.

Installing with Docker

Requirements

  • An x86-64 machine that stays on: a VPS, mini PC, NAS or a computer on your local network. The published image is linux/amd64; for ARM (e.g. a Raspberry Pi), build the image yourself.
  • Docker with the Docker Compose plugin (included in current installs).
  • For access over the internet: a domain or subdomain pointing at the machine, for HTTPS.

1. Create the files

Create a folder (for example polypodium-server) with a docker-compose.yml:

services:
  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: polypodium
      POSTGRES_USER: polypodium
      POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD is required}
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U polypodium -d polypodium"]
      interval: 5s
      timeout: 5s
      retries: 10

  server:
    # Pin a version (e.g. :3.1.0) to update only when you choose.
    image: ghcr.io/bruno1pb13/polypodium_server:latest
    restart: unless-stopped
    ports:
      # Localhost only: the reverse proxy is what faces the outside.
      # On a local network without a proxy, use "8080:8080".
      - "127.0.0.1:8080:8080"
    environment:
      DATABASE_URL: postgresql://polypodium:${DB_PASSWORD}@db/polypodium
      JWT_SECRET: ${JWT_SECRET:?JWT_SECRET is required}
      APP_ENV: production
      DB_SSL: "false"
      BEHIND_PROXY: "true"
      REGISTRATION_TOKEN: ${REGISTRATION_TOKEN:-}
      PHOTOS_DIR: /photos
    volumes:
      - photos_data:/photos
    depends_on:
      db:
        condition: service_healthy

volumes:
  db_data:
  photos_data:

And a .env in the same folder:

# PostgreSQL password (only used between the containers)
DB_PASSWORD=change-to-a-strong-password

# Signs the login tokens. At least 32 characters, unique per server.
# Generate one with:  openssl rand -base64 48
JWT_SECRET=change-to-a-long-random-key

# Recommended on the internet: protects creation of the first account.
# Generate one with:  openssl rand -hex 24
REGISTRATION_TOKEN=
Secrets. In production the server refuses to start if JWT_SECRET is missing, is the development value or is shorter than 32 characters. Changing JWT_SECRET later invalidates every session: devices have to sign in again (data is not affected). Don't commit the .env.

2. Start it

docker compose up -d
docker compose logs -f server      # Ctrl+C to stop following the logs

The first run creates the tables. The logs should show Database connected and migrations applied. and Polypodium server listening on http://0.0.0.0:8080. Check it:

curl http://localhost:8080/api/v1/health
# {"status":"ok","version":"1.0.0"}
Local network only? Change the port to "8080:8080" and, since there will be no proxy, use APP_ENV: development (which waives HTTPS) or keep BEHIND_PROXY: "true". In the app, the URL looks like http://192.168.0.10:8080. Skip to the first account. On the internet, HTTPS is a must: passwords and tokens travel with every request.

Using a PostgreSQL you already run

Remove the db service and point DATABASE_URL at your database. The user needs to be able to create tables, sequences and indexes in it. In production the connection uses SSL by default; if the database is on the same private network without SSL, set DB_SSL: "false".

DATABASE_URL: postgresql://user:password@db.example.lan:5432/polypodium

HTTPS and reverse proxy

With BEHIND_PROXY: "true" the server speaks plain HTTP and expects a proxy in front of it to handle TLS. In this mode it also trusts the X-Forwarded-For header for the client's IP, used by the login rate limit. That's why port 8080 must not be exposed: only the proxy (80/443) should be.

Caddy (the simplest)

Caddy gets and renews Let's Encrypt certificates by itself. With the domain pointing at the machine, the Caddyfile is three lines:

plants.yourdomain.com {
    reverse_proxy 127.0.0.1:8080
}

Nginx

Nginx caps request bodies at 1 MB by default, which blocks photos (up to 15 MB) and MCP calls carrying photos (up to ~41 MB). Raise client_max_body_size:

server {
    listen 443 ssl http2;
    server_name plants.yourdomain.com;

    ssl_certificate     /etc/letsencrypt/live/plants.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/plants.yourdomain.com/privkey.pem;

    client_max_body_size 50m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }
}

Other options

  • Nginx Proxy Manager: a graphical interface with Let's Encrypt. Under Advanced, add client_max_body_size 50m;.
  • Traefik, if you already use it: an HTTP router to the container's port 8080 is enough.
  • Cloudflare Tunnel: terminates TLS without opening ports. The free plan caps uploads at 100 MB, above what the server accepts.

No proxy: the server serves HTTPS

Replace BEHIND_PROXY with the certificate paths and mount the folder into the container:

    environment:
      BEHIND_PROXY: "false"
      SSL_CERT_PATH: /certs/fullchain.pem
      SSL_KEY_PATH: /certs/privkey.pem
    volumes:
      - photos_data:/photos
      - /etc/letsencrypt/live/plants.yourdomain.com:/certs:ro
    ports:
      - "443:8080"

The certificate is read at startup: after renewing it (e.g. with certbot), restart the container with docker compose restart server. In production the server requires one of the two options, proxy or certificate, and won't come up serving plain HTTP by mistake.

First account (admin)

The first account created on an empty server becomes the admin. From then on sign-up is closed (403 registration is closed) and other accounts can only be created by an admin, inside the app. Creation is guarded by a database lock: two simultaneous requests never produce two admins.

Without REGISTRATION_TOKEN

In the app, open Manage workspaces → Add remote workspace and enter the URL. The app calls GET /auth/status, sees there are no accounts yet and shows Create the server's first account. The password needs at least 8 characters.

With REGISTRATION_TOKEN (recommended on the internet)

Without the token, whoever reached a freshly installed server first would become admin. With it, the first account has to present it. The app doesn't send this token, so create the account through the API and then sign in normally in the app:

curl -X POST https://plants.yourdomain.com/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "email": "you@example.com",
    "password": "your-password-with-8+-characters",
    "registrationToken": "the-value-of-your-REGISTRATION_TOKEN"
  }'

Workspaces and gardens

In the app, everything to do with servers is under Manage workspaces (in the workspace selector at the top, or in Settings). A workspace is a separate set of plants and entries, with its own database on the device:

  • Local: always there, no account, never syncs. It's the default for anyone who has never connected a server.
  • Remote: an account on a server and one garden on that server. You can have several: different servers, different accounts or different gardens on the same server.

Adding a remote workspace

  1. Address. In Add remote workspace, enter the full URL, with http:// or https:// and the port if it isn't the default (https://plants.yourdomain.com or http://192.168.0.10:8080).
  2. Account. On an empty server, the app creates the first account (admin). Otherwise, sign in with email and password. Anyone without an account asks the admin, who creates it in the app.
  3. Name. Name the workspace (e.g. Home greenhouse). The name only applies on this device.
  4. Garden. If the account belongs to shared gardens, the app asks Which garden?. Each garden syncs in its own workspace.
  5. Local data. If the local workspace has data, the app offers Migrate local data: it copies plants, species, locations, entries and photos to the server. The local workspace stays on the device as it was.

At sign-in the app sends its deviceId. The server ties the device to the account and returns a session token valid for 30 days. When it expires, the app shows Session expired and the workspace offers Reconnect.

Shared gardens

A garden can have several accounts as members, all syncing the same plants. The personal garden can take members too.

  • New shared garden (workspace menu): creates an empty garden on the server, with you as owner, and opens it in a new workspace.
  • Garden members: the owner adds members by the email of an account that already exists on this server, and removes them. What a member recorded stays in the garden after they leave.
  • Open another garden: opens a garden the account already belongs to in a new workspace.
  • Leave garden: a member stops syncing; the data stays on the device. The owner can't leave their own garden.

How sync works

  • When. With Automatic sync on, every 5 minutes (30 in Android's battery saver). Or by hand, with Sync now.
  • Push. The app sends local changes in batches of up to 500 (POST /sync/receive) and uploads new photos (PUT /photos/…).
  • Pull. It asks for everything changed since its last cursor (GET /sync/changes?since=…), page by page, and downloads missing photos.
  • Conflicts. Each row keeps the real time of the edit (updatedAt). The latest edit wins, and on a tie the higher deviceId. The app and the server use the same rule (from the polypodium_core package), so they always reach the same result, with no conflict screen.
  • Deletes. Nothing is physically deleted: a delete becomes a tombstone (deletedAt) that propagates to the other devices.
  • Compatibility. The server only sends each device the entry types it declared it understands, and says which entity types it stores. That lets old app versions live alongside new ones in the same garden.

Weather forecast

Polypodium shows the forecast and the season for each location that has coordinates, and uses the data to adjust watering. The source is Open-Meteo, free and keyless. Who asks for it depends on the workspace:

Local workspaceRemote workspace
Who fetches the forecastThe device itselfOnly the server
Where it's turned onSettings → Weather forecastServer administration → Weather forecast
Open-Meteo receivesThe device's IP and coordinates rounded to ~1 kmThe server's IP and each region's center
Watering rulesTuned on the deviceSet by the admin, the same for everyone

In a remote workspace the device never calls Open-Meteo, even when the server has the forecast off. That way every member sees the same watering dates.

How the server fetches

  1. Turning it on. Off by default. When turned on, the first fetch starts right away.
  2. Regions. Every hour the server gathers the coordinates of every non-deleted location, across all gardens. A coordinate within WEATHER_CLUSTER_KM (5 km) of a region's center joins it; otherwise it creates a new region centered on itself. The center never moves afterwards. Each region makes a single request, and only the center goes to the provider.
  3. Frequency. A new region is fetched on the next check; others every WEATHER_REFRESH_HOURS (24 h). A failure is retried after 1 hour. Update now forces a fetch of all of them.
  4. Data requested. Hourly: temperature, humidity, rain, rain probability, weather code (WMO) and wind. Daily: the same plus max/min and ET0 (FAO-56 reference evapotranspiration). Each fetch covers at least 2 past days, which replace the old forecast with observed data.

A database lock keeps two instances from running the job at the same time.

Retention

To use another compatible instance (for example your own Open-Meteo), set WEATHER_API_URL. Region coordinates are never shown to members, because a region can group locations from different accounts; only admins see them, in GET /admin/weather.

Weather-adjusted watering

With the forecast on, each plant's next watering date is postponed or brought forward by the weather. The frequency you chose doesn't change, only the date, and the app shows why (e.g. “Watering postponed 2 days for rain”). It's on by default, together with the forecast.

Plants count when they are active, have a watering frequency, have been watered at least once and sit in a location with coordinates whose region already has a forecast.

The calculation

  • The plant's frequency is how long one watering lasts on a typical day: the day whose ET0 is the region's average over the last 30 days.
  • Each day after watering the plant uses day's ET0 ÷ average of a typical day, bounded between 50% and 200%. Hot, dry days bring watering forward; mild days push it back a little.
  • Only in locations marked Exposed to rain (outdoors, uncovered), rain gives back part of that: 70% of the millimetres, converted into typical days, never more than the plant has used since its last watering. Days under 2 mm don't count.
  • The plant is due on the day its use adds up to the frequency, rounded to the nearest day.
  • Past days use observed data. From today on, the latest forecast applies, with rain weighted by its probability and capped by what the previous day's forecast showed for the same date. Rain that only the newest forecast shows doesn't postpone anything yet.
  • Postpones by at most 7 days, never more than the frequency itself. Brings forward by at most 2 days, never more than half the frequency, and never to before today.

Tunable rules

In Server administration → Weather-adjusted watering (or PATCH /admin/watering). They apply to the whole server. Only changed values are saved; the rest follow the defaults of future versions.

AI access (MCP)

The server includes an MCP (Model Context Protocol) server. With it, assistants such as Claude and Cursor read a garden (plants, diary, photos, catalogs, weather) and, if you allow it, log care with photos, create and edit plants, cuttings, pots, species and locations, and repot plants. Changes reach devices on their next sync, like any other device's.

  1. Enable it on the server. Off by default. An admin turns it on in Server administration → AI access (MCP). While off, the endpoint answers 404 mcp_disabled and nobody can create tokens; existing tokens work again once it's back on.
  2. Create a token. In the workspace menu, AI access (MCP) → New token. Name it (e.g. Claude on my laptop) and choose whether it may make changes. The token (pmcp_…) is shown only once; the screen also shows the address and a ready-made Claude Code command.
  3. Connect the assistant with the address https://plants.yourdomain.com/api/v1/mcp and the header Authorization: Bearer pmcp_….

Token security

  • Each token gives access to a single garden and belongs to whoever created it. The token alone selects the garden.
  • Read only (the default) doesn't see the write tools. Read and write sees them all.
  • The server only keeps a SHA-256 hash. A lost token can't be recovered: revoke it and create another.
  • A token stops working at once if it's revoked, if the account is disabled or if it leaves the garden.
  • Up to 20 tokens per member per garden. The list shows when each was last used.

curl -X POST https://plants.yourdomain.com/api/v1/mcp \
  -H "Authorization: Bearer pmcp_…" \

  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

Protocol

Streamable HTTP transport (revisions 2025-06-18 and 2025-03-26), stateless: each JSON-RPC message is a POST, and the response is plain JSON, with no SSE and no session. Notifications get 202, batches are accepted, GET/DELETE answer 405, and a missing, invalid or revoked token gets 401 with WWW-Authenticate: Bearer. Methods: initialize, ping, tools/list, tools/call.

Authentication

Login returns a JWT valid for 30 days, carrying the account and the device. The account is re-checked in the database on every request, so disabled accounts lose access at once. /auth/* routes are rate-limited per IP: 20 requests per 300 s (429 with Retry-After).

GET /auth/status public

Whether the server has any accounts. The app uses it to choose between sign-in and the first account.

{ "hasUsers": false }

POST /auth/register public

Creates the first account, which becomes admin. After that it answers 403. registrationToken is only required when REGISTRATION_TOKEN is set.

// body
{ "email": "you@example.com", "password": "8+ characters", "registrationToken": "…" }
// 201
{ "token": "eyJ…", "userId": "…", "deviceId": "…", "role": "admin" }

POST /auth/login public

// body (deviceId and deviceName are optional)
{ "email": "you@example.com", "password": "…", "deviceId": "uuid", "deviceName": "Pixel 8" }
// 200
{ "token": "eyJ…", "userId": "…", "deviceId": "…", "role": "member" }

Without a deviceId, the server generates one. A deviceId belonging to another account gets 403 device belongs to another account. Wrong credentials and disabled accounts get 401; the response takes the same time whether or not the email exists.

Sync

State lives in versioned rows, one per (garden, entity). Every write gets a rev from a single server-wide sequence, so a pull is “everything with a rev above my cursor”. Entity types: species, plant, entry, entry_photo, location, soil, bed (pots), defensivo (pesticides), reminder.

// one change
{
  "entityType": "plant",
  "entityId": "uuid-generated-on-the-device",
  "payload": { … },
  "updatedAt": "2026-10-24T12:00:00.000Z",
  "deletedAt": null,
  "deviceId": "device-uuid",
  "rev": 42
}

GET /sync/changes?since=<rev>&limit=<n>&entities=<types>

The garden's rows with rev > since, in order. limit from 1 to 1000 (default 100). Repeat while hasMore is true, passing nextCursor as since.

{
  "changes": [ … ],
  "nextCursor": 57,
  "hasMore": false,
  "supportedEntities": ["bed", "defensivo", "entry", "entry_photo", "location",
                        "plant", "reminder", "soil", "species"]
}
  • X-Polypodium-Entry-Types: the server only sends entries (entry) of the listed types. Without the header, only the original 10 (irrigation, fertilizer, pruning, observation, height, chlorosis, pest, pesticide, other, history); old app versions would get stuck on an unknown type. Current types also include repotting and harvest.
  • entities restricts the pull to some entity types, and the response echoes it. The app uses this, with its own cursor, to fetch rows left behind once it learns a new type.
  • Both filters run in the query, so the cursor always advances and there's never an empty page with hasMore: true.

POST /sync/receive

Sends up to 500 changes. The body's deviceId must match the token's. The rev sent is ignored. A write older than the current row has no effect (and no error).

// body
{ "deviceId": "uuid", "changes": [ … ] }
// 200: types the server doesn't store are dropped and listed
{ "appliedCount": 3, "ignoredEntityTypes": [] }

POST /sync/ack

Records the highest rev the device has pulled from the garden (only moves forward). Informational.

{ "deviceId": "uuid", "cursor": 57 }

GET /sync/status

{ "pendingChangeCount": 4, "lastPulledCursor": 57, "serverLatestCursor": 61 }

Photos

The photoKey is a plain file name (no / or ..), referenced by the photoKey of entry and entry_photo entities. Each garden has its own folder under PHOTOS_DIR.

PUT /photos/<photoKey>

Body: the image bytes, up to MAX_PHOTO_BYTES (15 MB). Response { "ok": true, "photoKey": "…" }.

GET /photos/<photoKey>

The bytes, with a Content-Type from the extension (jpg, png, webp, gif).

HEAD /photos/<photoKey>

200 if it exists, 404 if not. The app uses it to avoid re-uploading what's already there.

Gardens

A garden the account doesn't belong to answers 404, without revealing whether it exists.

GET /gardens

{ "gardens": [
  { "id": "…", "name": "", "personal": true, "role": "owner",
    "ownerUserId": "…", "ownerEmail": "you@example.com" },
  { "id": "…", "name": "Vegetables", "personal": false, "role": "member",
    "ownerUserId": "…", "ownerEmail": "friend@example.com" }
] }

The personal garden comes first; its id is the userId.

POST /gardens

{ "name": "Vegetables" } (1 to 100 characters). 201 with the garden, you as owner.

PATCH /gardens/<id> owner

{ "name": "…" }.

GET /gardens/<id>/members

{ "members": [ { "userId": "…", "email": "…", "role": "owner", "addedAt": "…" } ] }

POST /gardens/<id>/members owner

{ "email": "…" } of an account on this server. 404 account not found, 409 already a member.

DELETE /gardens/<id>/members/<userId>

The owner removes; a member passes their own userId to leave. The owner can't leave their own garden (400).

MCP tokens

GET /gardens/<id>/mcp-tokens

A member sees their own tokens; the owner sees all of them. The secret never appears here. lastUsedAt is updated at most once a minute.

{ "enabled": true, "tokens": [
  { "id": "…", "name": "Claude Desktop", "tokenPrefix": "pmcp_Eggl_L", "canWrite": true,
    "createdAt": "…", "lastUsedAt": "…", "userId": "…", "email": "you@example.com" }
] }

POST /gardens/<id>/mcp-tokens

{ "name": "Claude Desktop", "canWrite": false }. 201 with the same fields plus token, shown only this once. 409 at the limit of 20; 403 mcp_disabled with MCP off.

DELETE /gardens/<id>/mcp-tokens/<tokenId>

Revokes it. A member revokes their own; the owner, any.

Admin

GET /admin/me any account

{ "role": "member", "disabled": false, "canExportData": true, "canImportData": true,
  "weatherEnabled": true, "mcpEnabled": false }

GET /admin/status

{ "uptimeSeconds": 86400, "version": "3.1.0", "userCount": 4,
  "latestVersion": "3.1.0", "updateAvailable": false }

GET PATCH /admin/settings

Fields: allowMemberExport, allowMemberImport (default true), weatherEnabled, mcpEnabled (default false). PATCH takes any subset and returns them all.

curl -X PATCH https://plants.yourdomain.com/api/v1/admin/settings \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"weatherEnabled": true, "mcpEnabled": true}'

GET /admin/users

{ "users": [ { "id": "…", "email": "…", "role": "admin", "disabled": false, "createdAt": "…" } ] }

POST /admin/users

{ "email": "…", "password": "8+ characters" }. Creates a member. 409 if the email exists.

PATCH /admin/users/<id>/role

{ "role": "admin" } or "member".

PATCH /admin/users/<id>/status

{ "disabled": true }. Demoting or disabling the last active admin: 400.

GET /admin/weather

Regions with coordinates, time zone, elevation, lastFetchedAt, lastAttemptAt, lastUsedAt and lastError.

POST /admin/weather/refresh

Fetches every region in use now. { "skipped": false, "regions": 3, "fetched": 3, "failed": 0 }; 409 with the forecast off.

GET PATCH /admin/watering

The watering rules plus enabled, with defaults and limits. PATCH takes any subset; null goes back to the default; an unknown or out-of-range field: 400.

Weather and watering

GET /weather/locations/<id>?days=7&months=0

Forecast for one of the garden's locations. days: past days in daily (default 7); months: full months in monthly (default 0). Hours and dates are in the region's time zone.

{
  "locationId": "…", "timezone": "America/Sao_Paulo", "elevation": 737.0,
  "fetchedAt": "2026-10-24T12:00:03.000Z",
  "hourly":  [{ "time": "2026-10-24T13:00", "temperature": 23.1, "humidity": 60,
                "precipitation": 0.0, "precipitationProbability": 10,
                "weatherCode": 2, "windSpeed": 9.4 }],
  "daily":   [{ "date": "2026-10-24", "weatherCode": 95, "temperatureMax": 23.6,
                "temperatureMin": 16.2, "precipitationSum": 22.9,
                "precipitationProbabilityMax": 100, "windSpeedMax": 10.1, "et0": 2.2 }],
  "monthly": [{ "month": "2026-09", "days": 30, "temperatureMaxAvg": 25.1,
                "temperatureMinAvg": 14.0, "temperatureMax": 31.2, "temperatureMin": 9.8,
                "precipitationSum": 88.4, "rainyDays": 9, "et0Sum": 96.0 }]
}

Errors, all 404 with a code: weather_disabled, location_not_found, no_coordinates, weather_pending (region not fetched yet).

GET /weather/watering

{
  "generatedAt": "2026-10-24T14:00:00.000Z",
  "plants": [{
    "plantId": "…", "locationId": "…",
    "lastWateredAt": "2026-10-21T08:30:00.000", "frequencyDays": 4,
    "exposedToRain": true,
    "dueDate": "2026-10-25", "adjustedDueDate": "2026-10-27",
    "shiftDays": 2, "reason": "rain", "rainMm": 12.4,
    "forecastFetchedAt": "2026-10-24T09:00:02.000Z"

}

shiftDays > 0 postpones (reason rain or cool); < 0 brings forward (heat). lastWateredAt and frequencyDays are the values used: the app only applies the shift while its own match. 404 weather_disabled or 404 watering_disabled make the app go back to the normal dates.

Health and errors

GET /health public

{ "status": "ok", "version": "1.0.0" }, where version is the API's. The server version is in /admin/status. Good for proxy or monitoring health checks.

Errors come as { "error": "message" }, sometimes with a stable code:

StatusWhen
400Invalid body, missing field, batch limit, rule out of range.
401No token, invalid or expired token, wrong credentials, disabled account.
403Not allowed: not an admin, not the owner, not a garden member, sign-up closed.
404Not found, or a feature turned off (weather_disabled, watering_disabled, mcp_disabled).
409Conflict: email already registered, already a member, token limit.
413Body over MAX_JSON_BODY_BYTES, MAX_PHOTO_BYTES or MAX_MCP_BODY_BYTES.
429Rate limit on /auth/*.

CORS: ALLOWED_ORIGINS is * by default; with a list, only listed origins are echoed back. The native app doesn't depend on CORS.

Building from source

The ready-made image suits almost everyone. Build it yourself to review the code, run without Docker, contribute or produce an image for another architecture.

Requirements

  • Stable Dart SDK 3.
  • git and access to GitHub: the shared polypodium_core package (conflict rule and weather calculation) is a git dependency, fetched by dart pub get.
  • PostgreSQL to run it and for the tests (the Compose setup uses version 16).

Running in development

git clone https://github.com/bruno1pb13/Polypodium_server.git
cd Polypodium_server
cp .env.example .env              # adjust DATABASE_URL
dart pub get
set -a; source .env; set +a
dart run bin/server.dart

With APP_ENV=development (the default) the server accepts HTTP, doesn't require SSL to the database and accepts the development JWT_SECRET.

Native binary

dart compile exe \
  -DSERVER_VERSION=$(git describe --tags --always | sed 's/^v//') \
  bin/server.dart -o polypodium_server

The binary doesn't need Dart to run. SERVER_VERSION is the version shown to admins and compared with the latest release; without it the version is dev, which is never reported as outdated.

Docker image

docker build --build-arg SERVER_VERSION=3.1.0 -t polypodium_server:3.1.0 .

# Another architecture (e.g. Raspberry Pi), with buildx:
docker buildx build --platform linux/arm64 \
  --build-arg SERVER_VERSION=3.1.0 -t polypodium_server:3.1.0-arm64 --load .

The Dockerfile compiles in a dart:stable image and copies only the binary into a debian:bookworm-slim one. The repository's docker-compose.yml builds locally: docker compose up -d --build.

Without Docker (systemd)

# /etc/polypodium/server.env
DATABASE_URL=postgresql://polypodium:password@localhost/polypodium
JWT_SECRET=…
APP_ENV=production
DB_SSL=false
BEHIND_PROXY=true
PHOTOS_DIR=/var/lib/polypodium/photos
PORT=8080
# /etc/systemd/system/polypodium.service
[Unit]
Description=Polypodium sync server
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
User=polypodium
EnvironmentFile=/etc/polypodium/server.env
ExecStart=/opt/polypodium/polypodium_server
Restart=on-failure

[Install]
WantedBy=multi-user.target
sudo useradd --system --home /var/lib/polypodium polypodium
sudo install -d -o polypodium /var/lib/polypodium/photos
sudo systemctl daemon-reload
sudo systemctl enable --now polypodium
journalctl -u polypodium -f

Tests

Warning: the tests use the database in DATABASE_URL and delete data. Never run them against a real database. 
docker run -d --name pp-test -p 5433:5432 \
  -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=polypodium postgres:16-alpine

export DATABASE_URL=postgresql://postgres:postgres@localhost:5433/polypodium
dart analyze --fatal-infos
dart test

Test files run one at a time (dart_test.yaml), because one file's migrations would deadlock against another's writes. CI runs analyze and test on every PR.

Releases

  • Every push to main publishes :latest, with the version from git describe (e.g. 3.1.0-3-gabc1234).
  • Publishing a vX.Y.Z release on GitHub publishes :X.Y.Z and :latest.

Backups and updates

Data lives in two places: PostgreSQL (everything but photos) and the photos volume. Back up both.

Backup

# Database
docker compose exec -T db pg_dump -U polypodium -d polypodium -Fc \
  > polypodium-$(date +%F).dump

# Photos
docker compose cp server:/photos ./photos-$(date +%F)

Automate it with cron and keep copies on another machine: a backup on the same disk doesn't protect against that disk failing. A daily example at 3 a.m.:

0 3 * * * cd /srv/polypodium-server && docker compose exec -T db pg_dump -U polypodium -d polypodium -Fc > backups/polypodium-$(date +\%F).dump

Restore

docker compose up -d db
docker compose exec -T db pg_restore -U polypodium -d polypodium --clean --if-exists \
  < polypodium-2026-10-24.dump
docker compose cp ./photos-2026-10-24/. server:/photos
docker compose up -d

For a plain SQL backup (pg_dump without -Fc), restore with psql into an empty database.

Updating

Back up first. Migrations run by themselves at startup, in one transaction: if something fails the database stays as it was and the server doesn't start. But a migrated database may not work with the previous version; going back means restoring the backup. 
docker compose pull
docker compose up -d
docker compose logs -f server

With a pinned image version, change the tag in docker-compose.yml first. Each version's notes are in the releases. The new-version notice in the app comes from a GitHub check every 12 h; on networks without internet, turn it off with UPDATE_CHECK=false.

Devices on older app versions keep syncing with newer servers: the server only sends them what they understand.

Troubleshooting

SymptomCause and fix
Server won't start: No TLS configuredIn production, set BEHIND_PROXY=true (with a proxy) or SSL_CERT_PATH and SSL_KEY_PATH.
Server won't start: JWT_SECRET …Use a random value of 32+ characters: openssl rand -base64 48.
SSL error connecting to the databaseDatabase without SSL on a private network: DB_SSL=false.
App: “Server unavailable or invalid URL”Check the scheme and port in the URL. Try curl https://…/api/v1/health from the same device/network.
Photos don't upload through the proxy (413)Raise the proxy's limit, e.g. client_max_body_size 50m; in Nginx.
Many 429s at loginBehind a proxy without BEHIND_PROXY=true, every client seems to come from the same IP. Or adjust AUTH_RATE_LIMIT_MAX.
registration is closedThe server already has accounts. Ask an admin to create yours.
“Session expired”The token lasts 30 days, or JWT_SECRET changed. Use Reconnect.
Location without a forecast (weather_pending)Its region hasn't been fetched yet: wait for the next hour or use Update now. Check lastError in GET /admin/weather.
Watering doesn't change with rainThe location needs coordinates and Exposed to rain, and the plant a frequency and a past watering.
MCP assistant gets 401 or 404401: wrong or revoked token, or the account left the garden. 404 mcp_disabled: an admin has to turn MCP on.
