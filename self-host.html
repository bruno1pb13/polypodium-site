Documentação do servidor

O Polypodium funciona 100% offline. O servidor é opcional: com ele você sincroniza a coleção entre aparelhos, tem um backup fora do celular, compartilha jardins com outras pessoas, recebe a previsão do tempo calculada num lugar só e conecta assistentes de IA. Esta página cobre da instalação à API.

Instalar em 5 minutosDocker Compose, imagem pronta, sem compilar nada. Conectar o appWorkspaces, contas e jardins compartilhados. Conectar uma IAClaude, Cursor e outros clientes MCP. Referência da APITodas as rotas de /api/v1.

Visão geral

O servidor é um único binário em Dart que fala HTTP/JSON e guarda tudo em PostgreSQL. As fotos ficam numa pasta em disco. Ele é distribuído como imagem Docker em ghcr.io/bruno1pb13/polypodium_server e o código é aberto, sob licença MIT, em github.com/bruno1pb13/Polypodium_server.

Conceitos

  • Conta. E-mail e senha no servidor. A primeira conta vira administradora e cria as demais; não existe cadastro público depois dela.
  • Jardim. O conjunto de dados que é sincronizado: plantas, espécies, locais, vasos, solos, registros do diário, fotos, defensivos e lembretes. Toda conta tem um jardim pessoal e pode criar outros para compartilhar com outras contas.
  • Workspace. O lado do app. Cada workspace é um banco separado no aparelho. O workspace local nunca sai do aparelho; cada workspace remoto sincroniza um jardim de um servidor. Trocar de workspace nunca mistura dados.
  • Aparelho. Cada instalação do app tem um deviceId. O servidor é apenas mais um par na sincronização: os IDs das entidades são gerados no aparelho e o servidor nunca os reatribui.

O que roda no servidor

ComponenteFunção
API REST /api/v1Login, sync (pull/push), fotos, jardins, administração, clima.

Instalação com Docker

Requisitos

  • Uma máquina x86-64 que fique ligada: VPS, mini-PC, NAS ou um computador da rede local. A imagem publicada é linux/amd64; para ARM (ex.: Raspberry Pi), faça o build da imagem.
  • Docker com o plugin Docker Compose (já incluído nas instalações atuais).
  • Para acesso pela internet: um domínio ou subdomínio apontando para a máquina, para o HTTPS.

1. Criar os arquivos

Crie uma pasta (por exemplo polypodium-server) com um docker-compose.yml:

services:
  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: polypodium
      POSTGRES_USER: polypodium
      POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD is required}
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U polypodium -d polypodium"]
      interval: 5s
      timeout: 5s
      retries: 10

  server:
    # Fixe uma versão (ex.: :3.1.0) para atualizar só quando quiser.
    image: ghcr.io/bruno1pb13/polypodium_server:latest
    restart: unless-stopped
    ports:
      # Só no localhost: quem acessa de fora é o proxy reverso.
      # Na rede local sem proxy, use "8080:8080".
      - "127.0.0.1:8080:8080"
    environment:
      DATABASE_URL: postgresql://polypodium:${DB_PASSWORD}@db/polypodium
      JWT_SECRET: ${JWT_SECRET:?JWT_SECRET is required}
      APP_ENV: production
      DB_SSL: "false"
      BEHIND_PROXY: "true"
      REGISTRATION_TOKEN: ${REGISTRATION_TOKEN:-}
      PHOTOS_DIR: /photos
    volumes:
      - photos_data:/photos
    depends_on:
      db:
        condition: service_healthy

volumes:
  db_data:
  photos_data:

E um .env na mesma pasta:

# Senha do PostgreSQL (usada só entre os contêineres)
DB_PASSWORD=troque-por-uma-senha-forte

# Assina os tokens de login. Mínimo de 32 caracteres, único por servidor.
# Gere com:  openssl rand -base64 48
JWT_SECRET=troque-por-uma-chave-aleatoria-bem-longa

# Recomendado na internet: protege a criação da primeira conta.
# Gere com:  openssl rand -hex 24
REGISTRATION_TOKEN=
Segredos. Em produção o servidor se recusa a iniciar se o JWT_SECRET estiver ausente, for o valor de desenvolvimento ou tiver menos de 32 caracteres. Trocar o JWT_SECRET depois invalida todas as sessões: os aparelhos precisam entrar de novo (os dados não são afetados). Não versione o .env.

2. Subir

docker compose up -d
docker compose logs -f server      # Ctrl+C para sair dos logs

Na primeira execução as tabelas são criadas. Os logs devem mostrar Database connected and migrations applied. e Polypodium server listening on http://0.0.0.0:8080. Confira:

curl http://localhost:8080/api/v1/health
# {"status":"ok","version":"1.0.0"}
Só na rede local? Troque a porta para "8080:8080" e, como não haverá proxy, use APP_ENV: development (que dispensa o HTTPS) ou mantenha BEHIND_PROXY: "true". No app, a URL fica algo como http://192.168.0.10:8080. Pule para a primeira conta. Na internet, HTTPS é obrigatório: senhas e tokens trafegam em cada requisição.

Usar um PostgreSQL que você já tem

Remova o serviço db e aponte DATABASE_URL para o seu banco . O usuário precisa poder criar tabelas, sequências e índices no banco. Em produção a conexão usa SSL por padrão; se o banco estiver na mesma rede privada e sem SSL, defina DB_SSL: "false".

DATABASE_URL: postgresql://usuario:senha@db.exemplo.lan:5432/polypodium

HTTPS e proxy reverso

Com BEHIND_PROXY: "true" o servidor fala HTTP puro e espera que um proxy na frente cuide do TLS. Nesse modo ele também confia no header X-Forwarded-For para saber o IP do cliente, usado no limite de tentativas de login. Por isso a porta 8080 não deve ficar exposta: só o proxy (80/443).

Caddy (o mais simples)

O Caddy obtém e renova os certificados Let's Encrypt sozinho. Com o domínio apontando para a máquina, o Caddyfile tem três linhas:

plantas.seudominio.com {
    reverse_proxy 127.0.0.1:8080
}

Nginx

O Nginx limita o corpo das requisições a 1 MB por padrão, o que barra as fotos (até 15 MB) e as chamadas MCP com fotos (até ~41 MB). Aumente o client_max_body_size:

server {
    listen 443 ssl http2;
    server_name plantas.seudominio.com;

    ssl_certificate     /etc/letsencrypt/live/plantas.seudominio.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/plantas.seudominio.com/privkey.pem;

    client_max_body_size 50m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }
}

Outras opções

  • Nginx Proxy Manager: interface gráfica com Let's Encrypt. Em Advanced, adicione client_max_body_size 50m;.
  • Traefik, se você já o usa: um roteador HTTP para a porta 8080 do contêiner basta.
  • Cloudflare Tunnel: termina o TLS sem abrir portas. O plano gratuito limita o upload a 100 MB, acima do que o servidor aceita.

Sem proxy: o servidor serve HTTPS

Troque BEHIND_PROXY pelos caminhos do certificado e monte a pasta no contêiner:

    environment:
      BEHIND_PROXY: "false"
      SSL_CERT_PATH: /certs/fullchain.pem
      SSL_KEY_PATH: /certs/privkey.pem
    volumes:
      - photos_data:/photos
      - /etc/letsencrypt/live/plantas.seudominio.com:/certs:ro
    ports:
      - "443:8080"

O certificado é lido na inicialização: depois de renovar (ex.: com certbot), reinicie o contêiner com docker compose restart server. Em produção o servidor exige uma das duas opções, proxy ou certificado, e não sobe servindo HTTP puro por engano.

Primeira conta (administrador)

A primeira conta criada num servidor vazio vira administradora. A partir daí o cadastro se fecha (403 registration is closed) e as outras contas só são criadas por um admin, dentro do app. A criação é protegida por um lock no banco: duas requisições simultâneas nunca geram dois admins.

Sem REGISTRATION_TOKEN

No app, abra Gerenciar workspaces → Adicionar workspace remoto e informe a URL. O app consulta GET /auth/status, vê que ainda não há contas e mostra Criar primeira conta do servidor. A senha precisa ter pelo menos 8 caracteres.

Com REGISTRATION_TOKEN (recomendado na internet)

Sem o token, qualquer pessoa que chegasse primeiro ao servidor recém-instalado viraria admin. Com ele, a primeira conta precisa apresentá-lo. O app não envia esse token, então crie a conta pela API e depois entre normalmente pelo app:

curl -X POST https://plantas.seudominio.com/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "email": "voce@exemplo.com",
    "password": "sua-senha-com-8+-caracteres",
    "registrationToken": "o-valor-do-seu-REGISTRATION_TOKEN"
  }'

Workspaces e jardins

No app, tudo o que envolve servidores fica em Gerenciar workspaces (no seletor de workspace, no topo, ou em Configurações). Um workspace é um conjunto separado de plantas e registros, com seu próprio banco no aparelho:

  • Local: sempre existe, não tem conta e não sincroniza. É o padrão de quem nunca conectou um servidor.
  • Remoto: uma conta num servidor e um jardim desse servidor. Você pode ter vários: servidores diferentes, contas diferentes ou jardins diferentes do mesmo servidor.

Adicionar um workspace remoto

  1. Endereço. Em Adicionar workspace remoto, informe a URL completa, com http:// ou https:// e a porta se não for a padrão (https://plantas.seudominio.com ou http://192.168.0.10:8080).
  2. Conta. Num servidor vazio, o app cria a primeira conta (admin). Senão, entre com e-mail e senha. Quem ainda não tem conta pede ao administrador, que a cria pelo app.
  3. Nome. Dê um nome ao workspace (ex.: Estufa de casa). Ele vale só neste aparelho.
  4. Jardim. Se a conta participa de jardins compartilhados, o app pergunta Qual jardim?. Cada jardim sincroniza no seu próprio workspace.
  5. Dados locais. Se o workspace local tem dados, o app oferece Migrar dados locais: copia plantas, espécies, locais, registros e fotos para o servidor. O workspace local continua no aparelho como estava.

No login o app manda o seu deviceId. O servidor associa o aparelho à conta e devolve um token de sessão válido por 30 dias. Quando ele expira, o app mostra Sessão expirada e o workspace oferece Reconectar.

Jardins compartilhados

Um jardim pode ter várias contas como membros, e todas sincronizam as mesmas plantas. O jardim pessoal também pode receber membros.

  • Novo jardim compartilhado (menu do workspace): cria um jardim vazio no servidor, com você como dono, e o abre num novo workspace.
  • Membros do jardim: o dono adiciona pelo e-mail de uma conta que já existe neste servidor e remove membros. O que um membro registrou continua no jardim depois que ele sai.
  • Abrir outro jardim: abre num novo workspace um jardim do qual a conta já é membro.
  • Sair do jardim: um membro deixa de sincronizar; os dados ficam no aparelho. O dono não pode sair do próprio jardim.

Como o sync funciona

  • Quando. Com a Sincronização automática ligada, a cada 5 minutos (30 no modo de economia de bateria do Android). Ou manualmente, em Sincronizar agora.
  • Envio. O app manda as mudanças locais em lotes de até 500 (POST /sync/receive) e sobe as fotos novas (PUT /photos/…).
  • Recebimento. Pede tudo o que mudou desde o último cursor (GET /sync/changes?since=…), página a página, e baixa as fotos que faltam.
  • Conflitos. Cada linha guarda a hora real da edição (updatedAt). Vence a edição mais recente e, no empate, o maior deviceId. O app e o servidor usam a mesma regra (do pacote polypodium_core), então sempre chegam ao mesmo resultado, sem tela de conflito.
  • Exclusões. Nada é apagado fisicamente: uma exclusão vira um tombstone (deletedAt) que se propaga aos outros aparelhos.
  • Compatibilidade. O servidor só envia a cada aparelho os tipos de registro que ele declarou entender, e diz quais tipos de entidade guarda. Assim versões antigas do app convivem com as novas no mesmo jardim.

Previsão do tempo

O Polypodium mostra a previsão e a estação do ano em cada local que tem coordenadas, e usa os dados para ajustar a rega. A fonte é o Open-Meteo, gratuito e sem chave. Quem consulta depende do workspace:

Workspace localWorkspace remoto
Quem busca a previsãoO próprio aparelhoSó o servidor
Onde ligaConfigurações → Previsão do tempoAdministração do servidor → Previsão do tempo
O Open-Meteo recebeO IP do aparelho e as coordenadas arredondadas (~1 km)O IP do servidor e o centro de cada região
Regras da regaAjustadas no aparelhoDefinidas pelo admin, iguais para todos

Num workspace remoto o aparelho nunca consulta o Open-Meteo, mesmo com a previsão desligada no servidor. Assim todos os membros veem as mesmas datas de rega.

Como o servidor busca

  1. Ligar. Desligada por padrão. Ao ligar, a primeira busca começa na hora.
  2. Regiões. A cada hora o servidor junta as coordenadas de todos os locais não excluídos, de todos os jardins. Uma coordenada a até WEATHER_CLUSTER_KM (5 km) do centro de uma região entra nela; senão cria uma região nova, centrada nela. O centro não muda depois. Cada região gera uma única consulta, e só o centro vai ao provedor.
  3. Frequência. Região nova é buscada na verificação seguinte; as outras, a cada WEATHER_REFRESH_HOURS (24 h). Uma falha é tentada de novo depois de 1 hora. Atualizar agora força a busca de todas.
  4. Dados pedidos. Por hora: temperatura, umidade, chuva, probabilidade de chuva, código do tempo (WMO) e vento. Por dia: o mesmo, mais máxima/mínima e ET0 (evapotranspiração de referência FAO-56). Cada busca inclui pelo menos 2 dias passados, que substituem a previsão antiga pelo observado.

Um lock no banco impede que duas instâncias rodem a busca ao mesmo tempo.

Para usar outra instância compatível (por exemplo, um Open-Meteo próprio), defina WEATHER_API_URL. As coordenadas das regiões nunca aparecem para os membros, porque uma região pode reunir locais de contas diferentes; só os admins as veem em GET /admin/weather.

Rega pelo clima

Com a previsão ligada, a data da próxima rega de cada planta é adiada ou adiantada pelo clima. A frequência que você escolheu não muda; só a data, e o app mostra o motivo (ex.: “Rega adiada 2 dias pela chuva”). Vem ligada junto com a previsão.

Entram no cálculo as plantas ativas, com frequência de rega, já regadas alguma vez e num local com coordenadas cuja região já tem previsão.

O cálculo

  • A frequência da planta é quanto dura uma rega num dia típico: o dia cuja ET0 é a média da região nos últimos 30 dias.
  • A cada dia depois da rega a planta gasta ET0 do dia ÷ média de um dia típico, limitado entre 50% e 200%. Dias quentes e secos adiantam; dias amenos adiam um pouco.
  • Só nos locais marcados como Exposto à chuva (ao ar livre, sem cobertura), a chuva devolve parte do gasto: 70% dos milímetros, convertidos em dias típicos, nunca mais do que a planta gastou desde a última rega. Dias com menos de 2 mm não contam.
  • A planta vence no dia em que o gasto soma a frequência, arredondado ao dia mais próximo.
  • Dias passados usam o observado. De hoje em diante vale a previsão mais recente, com a chuva multiplicada pela probabilidade e limitada ao que a previsão do dia anterior mostrava para a mesma data. Uma chuva que só a previsão mais nova mostra ainda não adia nada.
  • Adia no máximo 7 dias, nunca mais que a própria frequência. Adianta no máximo 2 dias, nunca mais que metade da frequência, e nunca para antes de hoje.

Acesso por IA (MCP)

O servidor inclui um servidor MCP (Model Context Protocol). Com ele, assistentes como Claude e Cursor leem um jardim (plantas, diário, fotos, catálogos, previsão do tempo) e, se você permitir, registram cuidados com fotos, criam e editam plantas, mudas, vasos, espécies e locais e fazem replantios. As mudanças chegam aos aparelhos no próximo sync, como as de qualquer outro aparelho.

  1. Ligar no servidor. Desligado por padrão. Um admin liga em Administração do servidor → Acesso por IA (MCP). Desligado, o endpoint responde 404 mcp_disabled e ninguém cria tokens; os tokens existentes voltam a valer quando ele é religado.
  2. Criar um token. No menu do workspace, Acesso por IA (MCP) → Novo token. Dê um nome (ex.: Claude no notebook) e escolha se ele pode fazer alterações. O token (pmcp_…) aparece uma vez só; a tela também mostra o endereço e o comando pronto para o Claude Code.
  3. Conectar o assistente com o endereço https://plantas.seudominio.com/api/v1/mcp e o header Authorization: Bearer pmcp_….

Segurança dos tokens

  • Cada token dá acesso a um único jardim e pertence a quem o criou. O token sozinho define o jardim.
  • Somente leitura (padrão) não vê as ferramentas de escrita. Leitura e escrita vê todas.
  • O servidor guarda só o hash SHA-256. Um token perdido não pode ser recuperado: revogue e crie outro.
  • O token para de valer na hora se for revogado, se a conta for desativada ou se ela sair do jardim.
  • Até 20 tokens por membro em cada jardim. A lista mostra o último uso de cada um.

Conectar assistentes

Claude Code

claude mcp add --transport http polypodium https://plantas.seudominio.com/api/v1/mcp \
  --header "Authorization: Bearer pmcp_…"

Claude Desktop

Pelo mcp-remote (precisa de Node.js), no claude_desktop_config.json:

{
  "mcpServers": {
    "polypodium": {
      "command": "npx",
      "args": [
        "mcp-remote",
        "https://plantas.seudominio.com/api/v1/mcp",
        "--header",
        "Authorization:${POLYPODIUM_AUTH}"
      ],
      "env": { "POLYPODIUM_AUTH": "Bearer pmcp_…" }

O header vai numa variável de ambiente porque alguns sistemas quebram argumentos com espaço.

Cursor e outros clientes com HTTP

Em .cursor/mcp.json (ou no arquivo equivalente do seu cliente):

{
  "mcpServers": {
    "polypodium": {
      "url": "https://plantas.seudominio.com/api/v1/mcp",
      "headers": { "Authorization": "Bearer pmcp_…" }
    }
  }
}

Os conectores personalizados do claude.ai exigem login OAuth, que o servidor ainda não oferece.

  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

Protocolo

Transporte Streamable HTTP (revisões 2025-06-18 e 2025-03-26), sem estado: cada mensagem JSON-RPC é um POST, a resposta é JSON puro, sem SSE nem sessão. Notificações recebem 202, lotes são aceitos, GET/DELETE respondem 405, e um token ausente, inválido ou revogado recebe 401 com WWW-Authenticate: Bearer. Métodos: initialize, ping, tools/list, tools/call.

✎ = só para tokens com alterações permitidas.

Autenticação

O login devolve um JWT válido por 30 dias, com a conta e o aparelho. A conta é reconsultada no banco a cada requisição, então contas desativadas perdem o acesso na hora. As rotas /auth/* têm limite por IP: 20 requisições a cada 300 s (429 com Retry-After).

GET /auth/status público

Diz se o servidor já tem contas. O app usa para escolher entre login e primeira conta.

{ "hasUsers": false }

POST /auth/register público

Cria a primeira conta, que vira admin. Depois disso responde 403. registrationToken só é exigido com REGISTRATION_TOKEN definido.

// corpo
{ "email": "voce@exemplo.com", "password": "8+ caracteres", "registrationToken": "…" }
// 201
{ "token": "eyJ…", "userId": "…", "deviceId": "…", "role": "admin" }

POST /auth/login público

// corpo (deviceId e deviceName opcionais)
{ "email": "voce@exemplo.com", "password": "…", "deviceId": "uuid", "deviceName": "Pixel 8" }
// 200
{ "token": "eyJ…", "userId": "…", "deviceId": "…", "role": "member" }

Sem deviceId, o servidor gera um. Um deviceId de outra conta recebe 403 device belongs to another account. Credenciais erradas e contas desativadas recebem 401; a resposta leva o mesmo tempo exista ou não o e-mail.

Sync

O estado fica em linhas versionadas, uma por (jardim, entidade). Cada escrita recebe um rev de uma sequência única do servidor, então o pull é “tudo com rev maior que o meu cursor”. Tipos de entidade: species, plant, entry, entry_photo, location, soil, bed (vasos), defensivo, reminder.

// uma mudança (change)
{
  "entityType": "plant",
  "entityId": "uuid-gerado-no-aparelho",
  "payload": { … },
  "updatedAt": "2026-10-24T12:00:00.000Z",
  "deletedAt": null,
  "deviceId": "uuid-do-aparelho",
  "rev": 42
}

GET /sync/changes?since=<rev>&limit=<n>&entities=<tipos>

Linhas do jardim com rev > since, em ordem. limit de 1 a 1000 (padrão 100). Repita enquanto hasMore for true, usando nextCursor como since.

{
  "changes": [ … ],
  "nextCursor": 57,
  "hasMore": false,
  "supportedEntities": ["bed", "defensivo", "entry", "entry_photo", "location",
                        "plant", "reminder", "soil", "species"]
}
  • X-Polypodium-Entry-Types: o servidor só envia registros (entry) dos tipos listados. Sem o header, só os 10 originais (irrigation, fertilizer, pruning, observation, height, chlorosis, pest, pesticide, other, history); versões antigas do app travariam com um tipo desconhecido. Os tipos atuais incluem também repotting e harvest.
  • entities restringe o pull a alguns tipos de entidade, e a resposta o ecoa. O app usa isso, com cursor próprio, para buscar linhas que ficaram para trás quando passa a entender um tipo novo.
  • Os dois filtros rodam na consulta, então o cursor sempre avança e não há página vazia com hasMore: true.

POST /sync/receive

Envia até 500 mudanças. O deviceId do corpo precisa ser o do token. O rev enviado é ignorado. Uma escrita mais antiga que a linha atual não tem efeito (sem erro).

// corpo
{ "deviceId": "uuid", "changes": [ … ] }
// 200: tipos que o servidor não guarda são descartados e listados
{ "appliedCount": 3, "ignoredEntityTypes": [] }

POST /sync/ack

Registra o maior rev que o aparelho já puxou do jardim (só avança). Informativo.

{ "deviceId": "uuid", "cursor": 57 }

GET /sync/status

{ "pendingChangeCount": 4, "lastPulledCursor": 57, "serverLatestCursor": 61 }

Fotos

O photoKey é um nome de arquivo simples (sem / nem ..), referenciado pelo photoKey das entidades entry e entry_photo. Cada jardim tem a sua pasta em PHOTOS_DIR.

PUT /photos/<photoKey>

Corpo: os bytes da imagem, até MAX_PHOTO_BYTES (15 MB). Resposta { "ok": true, "photoKey": "…" }.

GET /photos/<photoKey>

Os bytes, com Content-Type pela extensão (jpg, png, webp, gif).

HEAD /photos/<photoKey>

200 se existe, 404 se não. O app usa para não reenviar o que já está lá.

Jardins

Um jardim do qual a conta não é membro responde 404, sem revelar se existe.

GET /gardens

{ "gardens": [

    "ownerUserId": "…", "ownerEmail": "voce@exemplo.com" },
  { "id": "…", "name": "Horta", "personal": false, "role": "member",
    "ownerUserId": "…", "ownerEmail": "amiga@exemplo.com" }

O jardim pessoal vem primeiro; o id dele é o userId.

POST /gardens

{ "name": "Horta" } (1 a 100 caracteres). 201 com o jardim, você como dono.

PATCH /gardens/<id> dono

{ "name": "…" }.

GET /gardens/<id>/members

{ "members": [ { "userId": "…", "email": "…", "role": "owner", "addedAt": "…" } ] }

POST /gardens/<id>/members dono

{ "email": "…" } de uma conta deste servidor. 404 account not found, 409 already a member.

DELETE /gardens/<id>/members/<userId>

O dono remove; um membro passa o próprio userId para sair. O dono não sai do próprio jardim (400).

Tokens MCP

GET /gardens/<id>/mcp-tokens

O membro vê os próprios tokens; o dono vê todos. O segredo nunca aparece aqui. lastUsedAt é atualizado no máximo uma vez por minuto.

{ "enabled": true, "tokens": [
  { "id": "…", "name": "Claude Desktop", "tokenPrefix": "pmcp_Eggl_L", "canWrite": true,
    "createdAt": "…", "lastUsedAt": "…", "userId": "…", "email": "voce@exemplo.com" }
] }

POST /gardens/<id>/mcp-tokens

{ "name": "Claude Desktop", "canWrite": false }. 201 com os mesmos campos e o token, mostrado só desta vez. 409 no limite de 20; 403 mcp_disabled com o MCP desligado.

DELETE /gardens/<id>/mcp-tokens/<tokenId>

Revoga. O membro revoga os próprios; o dono, qualquer um.

{ "users": [ { "id": "…", "email": "…", "role": "admin", "disabled": false, "createdAt": "…" } ] }

{ "email": "…", "password": "8+ caracteres" }. Cria um membro. 409 se o e-mail existe.

Regiões com coordenadas, fuso, altitude, lastFetchedAt, lastAttemptAt, lastUsedAt e lastError.

As regras da rega mais enabled, com defaults e limits. O PATCH aceita qualquer subconjunto; null volta ao padrão; campo desconhecido ou fora da faixa: 400.

Saúde e erros

GET /health público

{ "status": "ok", "version": "1.0.0" }, onde version é a da API. A versão do servidor fica em /admin/status. Bom para health checks do proxy ou de monitoramento.

Erros vêm como { "error": "mensagem" }, às vezes com um code estável:

StatusQuando
400Corpo inválido, campo faltando, limite de lote, regra fora da faixa.
401Sem token, token inválido ou expirado, credenciais erradas, conta desativada.
403Sem permissão: não é admin, não é dono, não é membro do jardim, cadastro fechado.
404Não encontrado, ou recurso desligado (weather_disabled, watering_disabled, mcp_disabled).
409Conflito: e-mail já cadastrado, já é membro, limite de tokens.
413Corpo acima de MAX_JSON_BODY_BYTES, MAX_PHOTO_BYTES ou MAX_MCP_BODY_BYTES.

CORS: ALLOWED_ORIGINS é * por padrão; com uma lista, só as origens listadas são ecoadas. O app nativo não depende de CORS.

Build a partir do código

A imagem pronta serve para quase todos. Compile você mesmo para revisar o código, rodar sem Docker, contribuir ou gerar uma imagem para outra arquitetura.

Requisitos

  • Dart SDK 3 estável.
  • git e acesso ao GitHub: o pacote compartilhado polypodium_core (regra de conflito e cálculo do clima) é uma dependência git, baixada pelo dart pub get.
  • PostgreSQL para rodar e para os testes (a imagem oficial do Compose usa a versão 16).

Rodar em desenvolvimento

git clone https://github.com/bruno1pb13/Polypodium_server.git
cd Polypodium_server
cp .env.example .env              # ajuste DATABASE_URL
dart pub get
set -a; source .env; set +a
dart run bin/server.dart

Com APP_ENV=development (o padrão) o servidor aceita HTTP, não exige SSL no banco e aceita o JWT_SECRET de desenvolvimento.

Binário nativo

dart compile exe \
  -DSERVER_VERSION=$(git describe --tags --always | sed 's/^v//') \
  bin/server.dart -o polypodium_server

O binário não depende do Dart para rodar. SERVER_VERSION é a versão mostrada aos admins e comparada com a última release; sem ela vale dev, que nunca é dado como desatualizado.

Imagem Docker

docker build --build-arg SERVER_VERSION=3.1.0 -t polypodium_server:3.1.0 .

# Outra arquitetura (ex.: Raspberry Pi), com buildx:
docker buildx build --platform linux/arm64 \
  --build-arg SERVER_VERSION=3.1.0 -t polypodium_server:3.1.0-arm64 --load .

O Dockerfile compila numa imagem dart:stable e copia só o binário para uma debian:bookworm-slim. O docker-compose.yml do repositório builda localmente: docker compose up -d --build.

Backups e atualização

Os dados vivem em dois lugares: o PostgreSQL (tudo menos as fotos) e o volume de fotos. Faça backup dos dois.

Backup

# Banco
docker compose exec -T db pg_dump -U polypodium -d polypodium -Fc \
  > polypodium-$(date +%F).dump

# Fotos
docker compose cp server:/photos ./fotos-$(date +%F)

Automatize com um cron e guarde as cópias em outra máquina: um backup no mesmo disco não protege contra a falha dele. Um exemplo diário às 3 h:

0 3 * * * cd /srv/polypodium-server && docker compose exec -T db pg_dump -U polypodium -d polypodium -Fc > backups/polypodium-$(date +\%F).dump

Restauração

docker compose up -d db
docker compose exec -T db pg_restore -U polypodium -d polypodium --clean --if-exists \
  < polypodium-2026-10-24.dump
docker compose cp ./fotos-2026-10-24/. server:/photos
docker compose up -d

Para um backup em SQL puro (pg_dump sem -Fc), restaure com psql num banco vazio.

Atualizar

Faça backup antes. As migrações rodam sozinhas na inicialização, numa transação: se algo falhar o banco fica como estava e o servidor não sobe. Mas um banco migrado pode não funcionar com a versão anterior; voltar exige restaurar o backup. 
docker compose pull
docker compose up -d
docker compose logs -f server

Com uma versão fixa na imagem, troque a tag no docker-compose.yml antes. As notas de cada versão estão nas releases. O aviso de versão nova no app vem de uma consulta ao GitHub a cada 12 h; em redes sem internet, desligue com UPDATE_CHECK=false.

Aparelhos com versões antigas do app continuam sincronizando com servidores novos: o servidor só lhes envia o que eles entendem.
